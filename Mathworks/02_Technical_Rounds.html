Stage 2 — Technical Interview Rounds

PATTERN Expect 1–2 technical rounds, 45–60 minutes each, usually a live shared editor or a call with you writing code. Confidence: high on content themes, medium on count and format. Verify with your placement cell.

The MathWorks technical interview is not a LeetCode interview

This is the most important paragraph in this file. If you prepare for MathWorks the way you'd prepare for a product-company DSA gauntlet, you will over-index on the wrong thing.

MathWorks ships MATLAB and Simulink to engineers designing flight control laws, insulin pumps, and battery management systems. Their customers file bug reports that begin "our certification audit found..." The company is privately held, has no quarterly-growth pressure, and its cultural centre of gravity is correctness and maintainability over speed and cleverness.

The interview inherits that. PATTERN The observable consequences:

  • Coding questions are usually easy-to-medium, not hard. A string problem, a matrix problem, a tree traversal. What's hard is the follow-up conversation, not the algorithm.

  • They will ask "how would you test this?" — this is close to a MathWorks signature question, and it is where most candidates suddenly get vague. It's the single best place to differentiate yourself.

  • They will push on edge cases and invalid input before they push on complexity.

  • They care about API/interface design: what should this function be called, what should it take, what should it return, what should it do when given garbage.

  • They will watch whether you ask clarifying questions before coding. Diving straight into code is scored as a negative, not as decisiveness.

  • Code quality is graded: variable names, function decomposition, no magic numbers.

Behavioural rule for the whole round: narrate continuously. Silence reads as being stuck. "I'm thinking of two approaches — a hash map for O(n) time at O(n) space, or sorting for O(n log n) at O(1) extra. Given you said memory is tight, I'll sort. Let me confirm: can I mutate the input array?" That single sentence demonstrates trade-off reasoning, constraint-awareness, and requirement-checking. It's worth more than the code that follows.

Theme 1 — Testing (drill this hardest)

PATTERN Highest-yield, lowest-competition prep area. Everyone prepares DSA; almost nobody prepares this. MathWorks has entire teams whose job is quality engineering, and EDG rotations include testing.

The drill: for any function, produce 8–12 test cases in 90 seconds, organised by category. Practise until it's reflexive.

The universal edge-case checklist

Memorise this skeleton and apply it to anything:

  1. Empty / null — empty string, empty array, null pointer, zero-length input
  2. Single element — the boundary where most off-by-ones live
  3. Two elements — smallest case where order matters
  4. All identical elements
  5. Already sorted / reverse sorted
  6. Boundaries — 0, 1, -1, INT_MAX, INT_MIN, max allowed size
  7. Negatives and zero where the spec allows them
  8. Invalid input — wrong type, out-of-range index, malformed format
  9. Duplicates
  10. Very large input — performance and overflow
  11. Special characters / Unicode / whitespace for string functions
  12. Idempotence / round-trip — does decode(encode(x)) == x?

Worked example: "How would you test a function that reverses a string?"

A weak answer is "I'd test it with 'hello' and check I get 'olleh'." Here's a strong one:

"I'd split it into correctness, boundaries, invalid input, and non-functional.

Correctness: odd length ('abc' → 'cba'), even length ('abcd' → 'dcba'), a palindrome ('racecar' → unchanged, which also tests that I'm not accidentally returning the input untouched for the wrong reason). Boundaries: empty string → empty, single char → itself, two chars → swapped. Invalid/awkward: null pointer — and I'd want to know from the spec whether that's a crash, an empty return, or an error; string with embedded nulls; whitespace-only. Character-set: does 'reverse' mean bytes or characters? For UTF-8, naively reversing bytes corrupts multi-byte characters, and for combining characters like 'é' as e+accent, reversing separates them from their base. That's a spec question, not an implementation question. Non-functional: a very long string for performance and stack depth if the implementation is recursive; and I'd verify whether it reverses in place or returns a copy, since that changes the caller's contract. Round-trip: reverse twice should give the original — a cheap property test I can run over random inputs."

That answer takes 60 seconds and tells the interviewer you've thought about software, not just algorithms. Note especially the UTF-8 point and the in-place-vs-copy point: those are the two that make an interviewer sit up.

Practise these

  • How would you test sqrt(x)? (negatives, zero, perfect squares, huge values, precision — you can't use == on floats, you need |result² − x| < ε)
  • How would you test a matrix multiply? (dimension mismatch, 1×1, identity matrix as a known-answer oracle, non-square, empty, associativity as a property, floating-point accumulation order)
  • How would you test a date parser? (leap years, Feb 29 on non-leap years, 1900 vs 2000 century rule, timezones, "13th month", ambiguous DD/MM vs MM/DD)
  • How would you test a function with no return value that draws a plot? (this is a real MathWorks problem — answer: state-based assertions on the figure object, property queries, image-diff against a reference, and testing the data-transform layer separately from the rendering layer)
  • How would you test something non-deterministic? (seed the RNG for reproducibility, assert statistical properties over many runs rather than exact values, test invariants)

Vocabulary to have ready

Unit (one function, isolated, fast) · integration (components together) · system/end-to-end · regression (a test added when fixing a bug, so it never returns — MathWorks cares about this a lot) · smoke test · property-based testing · code coverage and its limit: 100% line coverage does not mean 100% behaviour coverage — you can execute every line and never test the empty-input path, and coverage says nothing about missing code · boundary value analysis · equivalence partitioning · mocking/stubbing · test oracle (how you know the right answer — sometimes the hardest part).

Theme 2 — API and interface design

PATTERN MathWorks designs functions used by millions of engineers who read the docs and expect stability for decades. So they ask design questions phrased as "design a function/class for X." They're evaluating whether you think about the caller.

The framework — apply to any design question

  1. Clarify the requirement first. Who calls this? How often? What's the expected input size? Single-threaded?

  2. Name it well. Names are part of the interface.

  3. Signature: parameter order (required before optional), types, const-correctness, return type.

  4. Error contract: invalid input → return code, exception, assert, or clamp? State a choice and justify it. There's no universally right answer, and the interviewer wants the reasoning.

  5. Edge/degenerate cases and what each does.

  6. Extensibility: what's the most likely future change, and does your design survive it without breaking callers?

  7. Documentation: what would the doc page say? (Very MathWorks.)

Likely prompts

  • Design a resizable array (vector) class. Cover: growth strategy (double the capacity → amortised O(1) push; explain the amortisation), size vs capacity, what operator[] does on out-of-range (fast unchecked) vs an at() that throws, copy constructor and destructor (deep copy — otherwise double-free), and iterator invalidation on reallocation.

  • Design classes for a matrix library. This is the MathWorks-flavoured one. Cover: dense vs sparse as separate implementations behind a common interface, storage order (see numerics below), operator overloading for + and *, dimension-mismatch errors, whether transpose returns a copy or a lightweight view, and element type as a template parameter.

  • Design a file reader supporting CSV, JSON and XML. Abstract base with a parse() method, one subclass per format, factory selecting on extension or content sniffing. Discuss streaming vs loading whole file into memory for large files.

  • Design a plotting API. Figure/axes/series object hierarchy, sensible defaults so the simple case is one line, and progressive disclosure of options for the complex case.

  • Design a logging system. Levels, sinks, formatting, thread safety, and whether it should be async.

Principles to name explicitly

Single responsibility · composition over inheritance (be ready to say why: inheritance couples you to a base class's implementation, composition doesn't) · Liskov substitution (a subclass must be usable anywhere the base is — the classic violation is Square extends Rectangle with independent setWidth/setHeight) · make interfaces easy to use correctly and hard to use incorrectly · fail loudly and early rather than silently producing wrong numbers · backward compatibility as a real constraint.

Theme 3 — C/C++ depth

MY READ Your resume lists C and C++ with no project evidence. If you claim them, expect probing. Know these cold, or reduce the claim on your CV — an unsupported skills line is worse than a shorter one.

Pointers and references: a pointer is a variable holding an address, can be null, can be reassigned, needs dereferencing; a reference is an alias, must be initialised, cannot be reseated, no null reference. Passing a large object by const& avoids a copy.

const placement: const char* p — pointer to constant char, can't change the char, can move the pointer. char* const p — constant pointer, can change the char, can't move the pointer. const char* const p — neither. Read right to left. A const member function promises not to modify the object.

Virtual functions and vtables: virtual enables runtime dispatch; each polymorphic class has a vtable of function pointers, each object holds a vptr to it. Why a virtual destructor matters: delete through a base pointer without a virtual destructor only runs the base destructor — the derived part leaks. This is a top-5 interview question. Pure virtual (= 0) makes an abstract class.

Rule of three/five: if you manage a resource you need destructor, copy constructor and copy assignment (plus move constructor and move assignment in modern C++). Otherwise the default shallow copy gives two objects owning the same pointer → double free.

Shallow vs deep copy: shallow copies the pointer, deep copies the pointee. The classic bug.

Memory: stack (automatic, fast, small, LIFO, freed on scope exit) vs heap (manual/new, large, fragmentable). Stack overflow from deep or infinite recursion or huge local arrays. Failure modes to name: memory leak (allocated, never freed), dangling pointer (points to freed memory), double free, use-after-free, buffer overrun. Modern answer: unique_ptr/shared_ptr and RAII, so ownership is expressed in the type system rather than in comments.

RAII: acquire in the constructor, release in the destructor. Guarantees cleanup even on exceptions. The single most important C++ idiom — name it by name.

static's three meanings: file-scope (internal linkage), function-local persistent variable, class-level member shared across instances.

Copy vs move: move transfers ownership of internals instead of duplicating them, std::move casts to an rvalue reference. Matters for returning large containers.

Undefined behaviour: signed integer overflow, out-of-bounds access, dereferencing null, using an uninitialised variable, modifying a string literal. Worth saying that UB means the compiler may assume it never happens, which is why UB bugs manifest as impossible-seeming behaviour under optimisation.

Compilation: preprocess → compile → assemble → link. Header guards / #pragma once prevent double inclusion. Declaration vs definition. What a linker error means vs a compile error.

Theme 4 — Numerics and floating point

MY READ Underrated for MathWorks specifically. Their product is numerical computing; a candidate who understands floating point stands out immediately, and almost nobody prepares this.

Why 0.1 + 0.2 != 0.3: binary floating point can't represent 0.1 or 0.2 exactly, just as decimal can't represent 1/3. The errors don't cancel. Never compare floats with ==; compare fabs(a-b) < epsilon, and prefer a relative tolerance (fabs(a-b) <= eps * max(fabs(a), fabs(b))) because an absolute epsilon that's right at 1.0 is wrong at 1e9.

IEEE 754 essentials: sign, exponent, mantissa. float ≈ 7 decimal digits, double ≈ 15–16. Special values: +0/-0, ±Inf, NaN. NaN != NaN is true — that's how isnan works, and it breaks naive sorting and equality logic.

Catastrophic cancellation: subtracting two nearly equal numbers destroys significant digits. The standard example is the quadratic formula, where you use the numerically stable rearrangement instead. Accumulation order matters: summing a large array of floats left-to-right accumulates error; pairwise or Kahan summation is better. Adding a tiny number to a huge one can be a no-op.

Row-major vs column-major. C/C++ arrays are row-major; MATLAB and Fortran are column-major. Consequence: iterating in the wrong order thrashes the cache, and it's why a naive loop nest can be several times slower than the same nest with the loops swapped. Knowing that MATLAB is column-major is a genuine "this person did their homework" signal.

Integer pitfalls: overflow (and that signed overflow is UB), integer division truncation, implicit signed/unsigned conversion making -1 > 1u true.

Theme 5 — Debugging and code reading

PATTERN Expect either "here's some code, what's wrong with it" or a scenario question. MathWorks does a lot of customer-reported-bug work, so debugging method matters.

Common planted bugs: off-by-one in a loop bound · = instead of == · uninitialised variable · integer division where a float was meant · missing break in a switch · modifying a container while iterating it · returning a pointer/reference to a local · shadowed variable · i <= v.size()-1 on an empty vector (unsigned underflow → huge number) · shallow copy where deep was needed · missing virtual destructor.

The scenario answer — "a customer reports a crash you can't reproduce": structure it as gather (exact version, platform, input data, stack trace, logs), then reproduce (the single most important step — get a minimal deterministic repro), then narrow (bisect the input, bisect the commit history with git bisect, add logging or assertions), then hypothesise-and-test one variable at a time, then fix the root cause not the symptom, then add a regression test so it can't come back, then check whether sibling code paths have the same bug. That last point — fixing it once where all callers route through, and checking for the same bug elsewhere — is exactly what a tools company wants to hear.

Mention tools by name: debugger with breakpoints and watchpoints, valgrind/AddressSanitizer for memory errors, profiler for performance, static analysis, and reverting to a known-good build to bound the regression.

Theme 6 — DSA question bank

PATTERN Expect easy-to-medium. Prioritise breadth and clean implementation over hard-problem depth.

Arrays and strings (highest frequency): two pointers · sliding window (longest substring without repeating characters) · prefix sums · Kadane's maximum subarray · Dutch national flag / sort colours · merge intervals · anagram grouping · palindrome checks · string tokenising and reversal of words in a sentence.

Hashing: two-sum · first non-repeating character · frequency counting · subarray with given sum · finding duplicates.

Binary search: on a sorted array, plus the variants that actually get asked — first and last occurrence, search in a rotated sorted array, square root by binary search, and binary search on the answer space.

Linked lists: reverse iteratively and recursively · detect a cycle (Floyd's tortoise and hare) and find its start · find the middle · merge two sorted lists · remove the nth node from the end.

Trees: all traversals including iterative versions · height and diameter · validate a BST (careful: the naive parent-comparison version is wrong; you need min/max bounds) · lowest common ancestor · level-order traversal · balanced-tree check.

Graphs — your home turf: BFS and DFS · shortest path in an unweighted graph via BFS · Dijkstra · A* · connected components · cycle detection · topological sort · flood fill and islands on a grid · shortest path in a maze with obstacles.

MY READ Your Warehouse PathMapper is exactly this territory. Make sure you can whiteboard A* from scratch in C++ — the open set as a priority queue, the closed set, g/h/f scores, and parent-pointer path reconstruction. Then be ready for "why A* over Dijkstra?" (a good heuristic prunes the search dramatically) and "what makes a heuristic admissible?" (never overestimates the true remaining cost, which is what guarantees optimality) and "what if it isn't admissible?" (faster, but you may return a suboptimal path — sometimes an acceptable trade). This is the strongest technical story on your resume; own it completely.

Matrices (MathWorks-flavoured, worth extra attention): rotate 90° in place · transpose in place · spiral traversal · set matrix zeroes without extra space · search a row-and-column-sorted matrix · matrix multiply and its complexity.

Sorting: know merge, quick and heap sort, their complexities, which are stable, quicksort's O(n²) worst case and how randomised pivoting fixes it in practice, why mergesort suits linked lists (no random access needed) and why quicksort suits arrays (cache locality, in-place).

Stacks and queues: balanced parentheses · min stack in O(1) · queue from two stacks · next greater element · evaluate postfix.

DP (medium at most): Fibonacci with memo vs tabulation · climbing stairs · coin change · longest common subsequence · edit distance · 0/1 knapsack · longest increasing subsequence. Be able to explain the recurrence and why the subproblems overlap; that matters more here than having 40 DP problems memorised.

Design-flavoured: LRU cache (hash map + doubly linked list) · a rate limiter · an autocomplete trie.

Theme 7 — Puzzles and estimation

PATTERN Occasional, not central. Think aloud; the process is the whole point.

Classics worth knowing: 3 bulbs and 3 switches with one trip upstairs (use heat) · 8 balls, one heavier, 2 weighings · 100 floors, 2 eggs, minimum worst-case drops · bridge crossing with one torch · 25 horses, 5 tracks, find the top 3 · two ropes burning unevenly to measure 45 minutes · Monty Hall (and be ready to explain why switching wins, since most people get the intuition wrong) · birthday paradox.

Estimation: "how many MATLAB licences are in use in India?" — state assumptions, decompose, do rough arithmetic, sanity-check the magnitude. They're grading structure, not the number.

Questions to ask your technical interviewer

Ending with a substantive question is a real signal. Have three ready:

  • "How does the team balance adding new capability against maintaining backward compatibility for users who've had scripts running for fifteen years?"
  • "What does the testing culture look like day to day — how much of a developer's time goes into tests versus features?"
  • "In the EDG rotations, how much choice do you get in where you rotate, and how do people usually end up finding their team?"

Avoid asking about salary, WFH policy, or appraisal cycles in the technical round. Save those for HR.

Round-day behaviours that get you marked up

Ask 2–3 clarifying questions before writing any code. State your assumptions out loud. Talk through the trade-off between two approaches before picking one. Write a brute force, say "this is O(n²), let me improve it," then improve it. Name your variables like an adult (leftIndex, not i2). Find your own bugs before the interviewer does — dry-run your code on a small input in front of them. Volunteer edge cases unprompted. When you're stuck, say what you're stuck on; when you get a hint, acknowledge it and use it visibly. If you don't know something, say so and then say how you'd find out.

And the things that get you cut: silence · coding before understanding · claiming a skill on your CV you can't discuss · defending a wrong answer after a correction · treating testing as an afterthought · ignoring the hint you were just given.
