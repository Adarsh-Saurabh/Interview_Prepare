05: Real-Time Credit Underwriting & Fraud ML System Design

Production architecture for sub-25ms credit limit decisioning and fraud detection processing thousands of transactions per second at CRED.

🎯 Latency Budget Breakdown (Target: $\le 25\text{ms}$ p99)
  • Network Hop & API Gateway Auth: $5\text{ms}$
  • Dual-Path Feature Retrieval (Feast Redis): $5\text{ms}$
  • Triton Model Inference (ONNX / LightGBM): $8\text{ms}$
  • Policy Rule Evaluation & Decisioning: $3\text{ms}$
  • Buffer & Margin: $4\text{ms}$

1. Dual-Path Feature Architecture

To avoid slow database joins during checkout, features are pre-materialized across distinct temporal layers:

Feature Category Engine Storage Backend Freshness SLA
Hot Features (e.g., 5-min spend velocity, device card count) Apache Flink Redis Cluster (Feast) < 5ms
Warm Features (e.g., 30-day category spend, login geography) Kafka Consumers Amazon DynamoDB < 30s
Cold Features (e.g., CIBIL bureau history, 12-month repayment score) Apache Spark / Airflow PostgreSQL / Snowflake Daily (24h)

2. High-Throughput Serving: Triton & ONNX

Python web frameworks (Flask/FastAPI) are prohibited on CRED's real-time payment paths due to GIL locking and high tail latencies. Models are compiled into ONNX and served via Triton Inference Server.

🛡️ Resilient Circuit Breaker Pattern

If Triton inference experiences high tail latency (> 20ms) or network timeout, the orchestrator immediately falls back to a deterministic safety rule engine (approving transactions for members with verified high credit scores and low velocity), ensuring zero user checkout blockage.
