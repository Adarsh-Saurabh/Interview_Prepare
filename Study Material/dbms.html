# NULL Three-Valued Logic & Production Gotchas

IMPORTANT Why 'WHERE col != NULL' Silently Returns Zero Rows
In ANSI SQL, NULL represents an *unknown* value, not zero or empty string. Comparison operators with NULL evaluate to **UNKNOWN** (Three-Valued Logic: TRUE, FALSE, UNKNOWN). • `WHERE col = NULL` or `WHERE col != NULL` both evaluate to UNKNOWN, which the WHERE clause filters out as falsy! Always use `IS NULL` or `IS NOT NULL`. • `COUNT(*)` counts total rows including NULLs. `COUNT(col)` counts only rows where `col IS NOT NULL`! • `WHERE id NOT IN (SELECT parent_id FROM t)`: If the subquery contains even a SINGLE row with `parent_id IS NULL`, the entire `NOT IN` condition collapses to UNKNOWN and returns 0 rows! Fix: Use `NOT EXISTS` instead.

# 🌲 Storage Engines: B+ Trees vs LSM Trees

# B+ Tree Storage Architecture: Fanout & Inode Mapping

B+ Tree Internal Nodes and Doubly Linked Leaf Nodes
🔍
TIP Why Databases Use B+ Trees Instead of Binary Search Trees or B-Trees
1. **Massive Fanout Minimizes Disk I/O**: A binary tree has fanout 2, requiring 30 disk seeks for 1 billion items. A B+ tree with 16KB page size and 8-byte keys has fanout ~1000, requiring only 3 disk reads! 2. **Internal Nodes Hold Only Keys**: Unlike standard B-trees which store record payloads in internal nodes, B+ trees store payloads exclusively in leaf pages. This maximizes internal node key capacity and keeps the tree shallow. 3. **Doubly Linked Leaf Level**: Leaves are connected via sequential pointers. Range scans (`BETWEEN 20 AND 80`) perform ONE root-to-leaf lookup, then scan horizontally in O(1) page traversals without ascending the tree.

# The Leftmost Prefix Rule for Composite Indexes

TIP Interview Query Analysis: INDEX(a, b, c)
A composite index creates a single B+ tree ordered lexicographically by `(a, then b, then c)`: • `WHERE a = 1 AND b = 2 AND c = 3` → ✅ Full Index Lookup on all 3 columns. • `WHERE a = 1 AND b = 2` → ✅ Index Lookup using prefix `(a, b)`. • `WHERE a = 1` → ✅ Index Lookup using prefix `(a)`. • `WHERE b = 2 AND c = 3` → ❌ Cannot use index lookup! The tree is sorted by `a` first; without filtering on `a`, it degrades to a Full Index Scan or Table Scan. • `WHERE a = 1 AND c = 3` → ⚠️ Uses index for `a = 1`, but cannot use index for `c` directly (Index Condition Pushdown evaluates `c`).

# 💾 WAL & ARIES Recovery Protocol (Durability)

# Write-Ahead Logging (WAL) & ARIES Crash Recovery

ARIES Recovery Pipeline: Analysis, Redo, and Undo Passes
🔍
IMPORTANT The Write-Ahead Logging Invariant
**Invariant**: Any dirty data page modified in the buffer pool must NEVER be flushed to disk until the corresponding log record in the WAL has been persisted to disk via `fsync()`. • **Steal Policy**: Buffer manager can flush dirty pages to disk before transaction commit to free RAM. (Requires Undo Log to rollback if aborted). • **No-Force Policy**: Buffer manager does NOT force dirty pages to disk at transaction commit; only the WAL is forced. (Requires Redo Log to replay changes on restart). • ARIES crash recovery executes in 3 sequential passes: (1) **Analysis** scans forward from checkpoint to identify active loser transactions and dirty pages, (2) **Redo** repeats history from earliest unwritten LSN to restore exact crash state, (3) **Undo** scans backward rolling back active uncommitted transactions.

TIP Write Skew Anomaly: Why Repeatable Read Fails Under MVCC
Write Skew occurs when two concurrent transactions read overlapping data sets, make decisions based on what they read, and write non-overlapping updates that together violate a global consistency constraint! **Classic Example (Hospital On-Call Doctors)**: Constraint: At least 1 doctor must be on call. Both Dr. Alice and Dr. Bob are currently on call (count = 2). • Transaction 1 (Dr. Alice): Checks `SELECT COUNT(*) WHERE on_call = true` (reads 2). Decides she can take leave: `UPDATE doctor SET on_call = false WHERE name = 'Alice'`; Commits. • Transaction 2 (Dr. Bob): Simultaneously checks `SELECT COUNT(*)` (reads 2 in his snapshot). Decides he can take leave: `UPDATE doctor SET on_call = false WHERE name = 'Bob'`; Commits. Both updates succeed because they updated different rows without write lock conflict! Result: ZERO doctors on call, violating the invariant! Snapshot Isolation / Repeatable Read permits this; only **Serializable** prevents it.

# 📐 Worked Derivations: Precedence Graphs & Normalization

# Worked Numerical 1: Conflict Serializability & Precedence Graphs

📐 WORKED PROBLEM

Conflict Serializability Test on Schedule S: R1(A), W2(A), R1(B), W3(B), R2(A), W1(B)

Step 1 Identify Conflicting Operations
Two operations conflict if they belong to different transactions, access the exact same data item, and at least one is a write operation.
Step 2 Conflict 1 (Item A)
R1(A) precedes W2(A) → Directed edge: T1 → T2.
Step 3 Conflict 2 (Item A)
W2(A) precedes R2(A) → Same transaction T2 (no edge).
Step 4 Conflict 3 (Item B)
W3(B) precedes W1(B) → Directed edge: T3 → T1.
Step 5 Conflict 4 (Item B)
R1(B) precedes W3(B) → Directed edge: T1 → T3.
Step 6 Cycle Detection
We have edge T3 → T1 and edge T1 → T3! There is a directed cycle between T1 and T3 (T1 ⇄ T3).
👁️ Click to Reveal Final Verification & Answer
Schedule S is NOT conflict-serializable because its precedence graph contains a directed cycle (T1 ⇄ T3). It cannot be transformed into any equivalent serial schedule.

# Worked Numerical 2: Functional Dependencies & BCNF Decomposition

📐 WORKED PROBLEM

Relation R(A, B, C, D, E) with FDs: { A → BC, CD → E, B → D, E → A }

Step 1 Find Candidate Keys
Attribute A closure: A+ = {A, B, C, D, E} → A is a Candidate Key! Attribute E closure: E+ = {E, A, B, C, D} → E is a Candidate Key! Attribute (B, C) closure: BC+ = {B, C, D, E, A} → BC is a Candidate Key!
Step 2 Check 3NF Condition
For every FD X → Y: either X is a superkey, or Y is a prime attribute (part of a candidate key). In B → D: B is not a superkey, but D is prime? Candidate keys are A, E, BC. Prime attributes: {A, B, C, E}. D is NOT prime! Violates 3NF.
Step 3 Check BCNF Condition
In B → D: B is not a superkey. Therefore R is NOT in BCNF.
Step 4 BCNF Decomposition
Decompose R on violating FD B → D into R1(B, D) with key B (in BCNF) and R2(A, B, C, E) with key A or E (in BCNF).
👁️ Click to Reveal Final Verification & Answer
Relation R is decomposed into R1(B, D) and R2(A, B, C, E), both satisfying BCNF with a lossless join decomposition.

# 🎯 High-Yield DBMS Engine Interview Flashcards

What is the difference between Clustered and Non-Clustered Indexes?
P0 Storage Systems
A Clustered Index dictates the physical on-disk storage order of table data rows. The leaf nodes of a clustered index contain the actual data rows themselves (e.g. primary key in InnoDB). A table can have only ONE clustered index. A Non-Clustered (Secondary) Index maintains a separate B+ tree where leaf nodes store the indexed key along with a pointer to the clustered index key (Primary Key in InnoDB) or disk RID. Looking up via non-clustered index requires a second lookup ('bookmark lookup') to fetch unindexed columns, unless it is a Covering Index.

How does MVCC (Multi-Version Concurrency Control) allow readers to not block writers?
P0 Transaction Internals
Instead of placing shared locks on data rows, MVCC creates a new timestamped version of a row whenever an UPDATE occurs. In InnoDB, each row contains hidden system columns: `DB_TRX_ID` (transaction ID that created the row) and `DB_ROLL_PTR` (pointer to the undo log record containing prior version). When a transaction reads under Repeatable Read, the engine establishes a Read View. If a row was modified after the Read View, the engine traverses the Undo Log version chain backwards to read the historical snapshot. Readers never acquire locks and writers never block readers!

What is the difference between DELETE, TRUNCATE, and DROP?
P0 Campus Classic
1. `DELETE`: DML operation. Scans and removes rows one by one, firing triggers and logging each row in the Undo/Redo log. Very slow on large tables; does NOT reset auto-increment or release disk space. Rollback-able. 2. `TRUNCATE`: DDL operation. Deallocates entire data pages directly and resets the high-water mark and auto-increment counter. Extremely fast. Rollback-ability varies: MySQL cannot rollback TRUNCATE; PostgreSQL and SQL Server CAN rollback TRUNCATE within a transaction! 3. `DROP`: DDL operation. Completely destroys table schema, indexes, constraints, and data pages from the database catalog.
Rate Recall:
Why is SELECT COUNT(*) slow in MySQL InnoDB but instant in MyISAM?
P0 Database Engines
MyISAM stores an exact row count counter in the table header metadata file (`.MYI`), returning `COUNT(*)` in O(1) time without reading data. However, InnoDB uses MVCC: different concurrent transactions can see different numbers of active rows simultaneously depending on their active Read Views and uncommitted transactions! Therefore, InnoDB must perform an actual index scan over the smallest available secondary index to count visible rows, which takes O(N) time.
