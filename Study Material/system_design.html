⚡ 10-Minute Rapid Recall Cheat Sheet

High-Level Design

1. CAP Theorem & PACELC Master Matrix

Classification Guarantees Under Partition (P) Behavior During Normal Operation (No Partition) Real-World Systems
CP (Consistency + Partition) Refuses requests or errors out to guarantee strict linearizable consistency across remaining nodes. Focuses on ACID consistency over lowest latency. Google Spanner, HBase, ZooKeeper, MongoDB (strict write majority).
AP (Availability + Partition) Always accepts reads and writes, returning potentially stale data (Eventual Consistency). Focuses on ultra-low read/write latency. Amazon DynamoDB, Apache Cassandra, CouchDB.
PACELC Theorem Extension If Partition (P): Choose Availability (A) OR Consistency (C).
Else (E): Choose Latency (L) OR Consistency (C).
Example: DynamoDB is PA/EL (Available under partition, Low latency under normal conditions).

2. Rate Limiting Algorithms Matrix

Algorithm How It Works Pros Cons / Pitfalls
Token Bucket Tokens added to bucket at constant rate $R$ up to capacity $B$. Request consumes 1 token. Allows short controlled bursts up to bucket capacity $B$; memory-efficient ($O(1)$ per user). Requires concurrency synchronization (handled via Redis Lua script).
Leaky Bucket Requests enter a FIFO queue and leak out at a strictly constant processing rate. Smooths traffic outflow to perfectly constant rate; ideal for message queues. Bursts are buffered or dropped even if backend is completely idle.
Sliding Window Counter Blends request count of current window and percentage of previous window: $\text{Count} = C_{curr} + C_{prev} \times (1 - \text{progress})$. Smooths out boundary burst spikes of Fixed Window without high memory cost of Sliding Log. Approximation based on uniform traffic assumption (near 99.9% accurate).

3. Caching Invalidation & Failure Modes Cheat Sheet

Cache Failure Mode Root Cause Impact Standard Production Fix
Cache Stampede (Thundering Herd) Hot cached key expires; 10,000 concurrent requests all miss cache and hit the database simultaneously! Database CPU spikes to 100%, causing cascading database failure. Distributed Mutex Lock (only 1 request queries DB while others wait) or Probabilistic Early Expiration (XFetch algorithm).
Cache Penetration Malicious or erroneous queries for keys that do NOT exist in DB (e.g. id = -9999). Every query bypasses cache and hits disk database every time! Bloom Filter in front of cache (returns "definitely not in DB" in $O(1)$) OR cache the null value with a short TTL.
Cache Avalanche Thousands of cached keys set with the identical expiration time (e.g. 1 hour) expire simultaneously. Sudden flood of massive queries overwhelms database at that exact minute. Add Random Jitter to expiration TTL: $\text{TTL} = \text{Base} + \text{rand}(0, 300\text{s})$.

🧠 Consistent Hashing, Rate Limiting & TinyURL

System Design Mechanics

1. Designing TinyURL: Base62 Encoding & Key Generation Service (KGS)

Scale & Capacity Estimations:
• Write volume: 500 million new URLs / month → ~200 writes / sec.
• Read volume: 100:1 read-to-write ratio → 20,000 reads / sec (20K QPS).
• Storage for 5 years: $500\text{M} \times 12 \times 5 = 30\text{ billion}$ records. At 500 bytes per record = 15 TB storage.

💡 Why Base62 Encoding instead of MD5/Base64?
  • Base64 uses characters [0-9a-zA-Z+/]. The symbols + and / have special reserved meanings in URLs and require encoding (e.g. %2B), breaking URL aesthetics.
  • Base62 uses only alphanumeric characters: [0-9a-zA-Z] (10 digits + 26 lowercase + 26 uppercase = 62 characters).
  • A 7-character string in Base62 produces: $62^7 = \mathbf{3,521,614,606,208}$ (3.52 Trillion) unique URLs, easily sufficient for centuries!

2. Resolving Hash Collisions: Key Generation Service (KGS)

If you hash long URLs using MD5/SHA256 and take the first 7 characters, different URLs can hash to the same 7 characters (Hash Collision). Retrying or appending sequence numbers causes race conditions in distributed clusters.

The KGS Solution: A dedicated standalone Key Generation Service pre-generates 7-character random unique strings offline and stores them in a database. When a server needs to shorten a URL, it grabs a batch of 1,000 pre-generated unique keys from KGS into local memory. Zero collisions, zero MD5 hash overhead, and instant $O(1)$ response time!

⚠️ High-Frequency Distributed Systems Traps

System Design Traps
Trap #1: L4 vs L7 Load Balancing — Which should you pick?

L4 (Transport Layer - TCP/UDP): Operates strictly on IP address and port numbers without inspecting the payload packet contents. Extremely fast, minimal CPU overhead (handles millions of packets/sec via Linux IPVS / AWS NLB). Cannot route based on HTTP headers, cookies, or URL paths.

L7 (Application Layer - HTTP/HTTPS): Terminates the TLS connection, parses the full HTTP request (URL paths, headers, JWT tokens). Enables smart routing (e.g. /api/v1/video → Video Service; /api/v1/auth → Auth Service), but consumes significantly more CPU memory for TLS decrypt and request parsing (e.g. AWS ALB, NGINX, HAProxy).

Trap #2: Push vs Pull Architecture for Social Feeds (The Celebrity Problem)

• Push Model (Fan-out-on-write): When User A posts a tweet, system pushes it to the home feed cache of all their followers. Reads are instant ($O(1)$). Catastrophic failure: When Elon Musk (200M followers) tweets, the server must write to 200,000,000 user feed mailboxes, creating a massive queue backlog!

• Hybrid Solution (Production Twitter/Instagram): Standard users use Push model. For "Celebrity" users with > 50,000 followers, do NOT fan out their posts! When a follower opens their feed, the system pulls the celebrity's recent tweets and merges them with the follower's feed in-memory at read time (Fan-out-on-read).

🎯 10 High-Frequency GFG Interview Q&As (Self-Assessment)

10 Questions
Q1: What is Consistent Hashing and why does adding a node only redistribute K/N keys?
In standard hashing (hash(key) % N), changing $N$ (adding or removing a server) changes the modulus denominator for almost 100% of keys, invalidating the entire cache fleet and causing a database crash.

In Consistent Hashing, both servers and keys are hashed onto the same circular ring ($0$ to $2^{32}-1$). A key belongs to the first server encountered clockwise. When a new server is added, it only claims keys between itself and its predecessor on the ring. Thus, on average, only $K/N$ keys move (where $K = \text{total keys}$, $N = \text{total servers}$)!
Q2: How does Apache Kafka achieve its massive throughput?
Kafka achieves throughput of millions of messages/sec on commodity hardware through 4 architectural design choices:
  1. Sequential Disk I/O: Kafka appends messages sequentially to an immutable commit log. Sequential disk access is as fast as random memory access on modern NVMe drives.
  2. OS Page Cache: Messages are cached in the Linux OS page cache rather than Java JVM heap, eliminating JVM garbage collection pauses.
  3. Zero-Copy Transfer: Uses the Linux sendfile() system call to transfer data directly from OS page cache to network socket buffer, bypassing user-space CPU memory copying.
  4. Batching & Compression: Producers batch messages into chunks and compress them (Snappy, LZ4) before network transmission.
Q3: What are the differences between WebSockets, Long Polling, and Server-Sent Events (SSE)?
• Short Polling: Client repeatedly sends HTTP requests at fixed intervals (high overhead, mostly empty responses).
• Long Polling: Client sends HTTP request; server holds connection open until new data is available or timeout occurs.
• WebSockets: Full-duplex, bi-directional persistent TCP connection initiated via HTTP upgrade handshake. Ideal for real-time multiplayer games, live trading order books (Pace Stock Broking), and chat apps.
• Server-Sent Events (SSE): Monodirectional stream from server to client over HTTP (client cannot send data over the same connection). Ideal for live sports ticker updates, stock price feeds, and LLM text streaming (ChatGPT/Gemini).
Q4: How do you implement a distributed Rate Limiter in Redis without race conditions?
To enforce an atomic sliding window rate limit without race conditions between concurrent requests, use a Redis Lua Script: 
-- Redis Lua script for Sliding Window Rate Limiter
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local clearBefore = now - window

-- 1. Remove timestamps older than current window
redis.call('ZREMRANGEBYSCORE', key, 0, clearBefore)
-- 2. Count current elements in window
local currentRequests = redis.call('ZCARD', key)

if currentRequests < limit then
    redis.call('ZADD', key, now, now)
    redis.call('EXPIRE', key, window)
    return 1 -- Allowed
else
    return 0 -- Throttled
end
Because Redis executes Lua scripts atomically in a single thread, no locks are required!
Q5: What is the difference between Strong Consistency, Eventual Consistency, and Read-Your-Writes?
• Strong (Linearizable) Consistency: Any read following a write is guaranteed to return the updated value across all replicas. Requires synchronous replication and consensus (Paxos/Raft). High write latency.
• Eventual Consistency: Replicas converge to the same value over time if no new updates are made. Reads immediately after a write may return stale data. High availability and low latency.
• Read-Your-Writes (Monotonic Read) Consistency: Guarantees that a user will always see their own updates immediately (e.g. posting a comment shows up on the author's screen immediately even if other users see it 3 seconds later).
Q6: What are Bloom Filters and how do they prevent Cache Penetration?
A Bloom Filter is a space-efficient probabilistic data structure that tests whether an element is a member of a set using a bit array of size $m$ and $k$ independent hash functions.
• Guarantees: Zero False Negatives (If it says an item is NOT in the database, it is 100% definitely NOT in the database!). Small probability of False Positives.
• Usage in Caching: When a request for key $X$ arrives, check the Bloom Filter first. If the Bloom filter returns "false", reject the request immediately with HTTP 404 without querying Redis or touching the SQL database!
Q7: How do you design an Idempotent API?
An operation is idempotent if making the request multiple times produces the identical side-effect as making it once (essential for payment processing when network drops mid-request).
• Implementation: Client generates a unique UUID Idempotency Key (e.g. in HTTP header Idempotency-Key: 123e4567-e89b...).
• Server stores the idempotency key in a Redis/SQL distributed lock with state (PROCESSING / COMPLETED).
• If a duplicate request arrives while processing, reject or wait; if already completed, return the cached successful response without re-charging the credit card!
Q8: How does a Content Delivery Network (CDN) route requests using Anycast?
In Anycast BGP Routing, multiple CDN edge servers located across different geographical continents share the exact same single IP address.
When a user queries the IP, internet border routers route the packets to the geographically closest edge server via the shortest BGP autonomous system (AS) hop count. Static assets (images, video chunks, CSS) are served from local edge RAM/SSD in < 10ms without crossing ocean cables!
Q9: Explain the Two-Phase Commit (2PC) Protocol and its biggest flaw.
2PC coordinates atomic distributed transactions across multiple database nodes:
  • Phase 1 (Prepare): Coordinator sends PREPARE to all cohorts. Cohorts execute transaction, write to undo/redo logs, lock resources, and reply YES or NO.
  • Phase 2 (Commit): If ALL cohorts vote YES, coordinator sends COMMIT. If any cohort votes NO, coordinator sends ROLLBACK.
Biggest Flaw (Blocking Coordinator Failure): If the coordinator crashes mid-commit after cohorts locked their resources, cohorts are permanently blocked in uncertainty, holding table locks and freezing the system! (Modern systems use Saga Pattern or Raft consensus instead).
Q10: What is Database Sharding and how do you choose a Shard Key?
Database Sharding partitions large database tables horizontally across distinct physical database servers.
Shard Key Selection Criteria:
  • High Cardinality: Keys must have millions of distinct values (e.g. user_id vs low-cardinality country).
  • Uniform Data Distribution: Avoids "hotspot shards" where 90% of traffic hits one physical machine.
  • Query Isolation: Choose a key that groups frequently queried data on the same shard to avoid costly distributed cross-shard joins (Scatter-Gather queries).
