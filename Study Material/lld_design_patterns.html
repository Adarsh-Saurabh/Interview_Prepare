OOD & Patterns

1. SOLID Principles Master Matrix

Principle Formal Rule Common Violation (Anti-Pattern) Refactored Solution
S - Single Responsibility A class should have one, and only one, reason to change. A User class that manages user properties, writes to database, AND sends welcome emails. Separate into User (model), UserRepository (database), and EmailService (notifications).
O - Open / Closed Software entities should be open for extension, but closed for modification. Using giant if/else or switch blocks to calculate discounts for each new customer type. Use the Strategy Pattern or Polymorphism with a common DiscountStrategy interface.
L - Liskov Substitution Subtypes must be substitutable for their base types without altering program correctness. Square inherits from Rectangle: setting width alters height, breaking client expectations! Do not inherit Square from Rectangle; have both implement a shared Shape interface with getArea().
I - Interface Segregation Clients should not be forced to depend upon interfaces they do not use (fat interfaces). A monolithic Machine interface with print(), scan(), and fax() forced onto a simple printer. Split into fine-grained interfaces: Printer, Scanner, and FaxMachine.
D - Dependency Inversion High-level modules should not depend on low-level modules; both should depend on abstractions. A PaymentProcessor directly instantiating new StripeClient() inside its constructor. Inject a PaymentGateway interface into PaymentProcessor (Dependency Injection).

2. Top 10 High-Frequency Design Patterns Cheat Sheet

Pattern Category Intent / Core Mechanism Real-World / Standard Library Example
Singleton Creational Ensures a class has only one instance and provides a global access point. Thread-safe Database Connection Pool, Logger, Hardware device driver.
Factory Method Creational Defines an interface for creating objects, letting subclasses decide which class to instantiate. LoggerFactory.getLogger(), Cross-platform GUI button creation.
Builder Creational Constructs complex objects step-by-step, avoiding telescopic constructors with 10+ arguments. HttpRequest.newBuilder().uri(...).GET().build().
Adapter Structural Converts the interface of a legacy or third-party class into another interface clients expect. Arrays.asList(), wrapping a legacy XML payment API to conform to JSON interface.
Decorator Structural Attaches additional responsibilities to an object dynamically without subclassing. Java I/O: new BufferedReader(new FileReader("file.txt")); Python function decorators.
Proxy Structural Provides a surrogate or placeholder for another object to control access, caching, or lazy loading. Hibernate Lazy Loading proxy, Virtual Proxy, Protection Proxy (auth checks).
Strategy Behavioral Defines a family of interchangeable algorithms and makes them interchangeable at runtime. Collections.sort(list, Comparator), Payment strategies (CreditCard, PayPal, UPI).
Observer Behavioral Defines a one-to-many dependency so that when one object changes state, all dependents are notified. GUI Event Listeners, Kafka Event Bus, Reactive Streams, Model-View-Controller (MVC).

🧠 SOLID, LRU Cache & Design Patterns

Low-Level Code Implementations

1. Complete Production-Grade LRU Cache Implementation (C++)

Combining std::unordered_map for $O(1)$ search and a DoublyLinkedList with dummy head and tail nodes to avoid edge-case null checks: 

#include <unordered_map>

class LRUCache {
    struct Node {
        int key, val;
        Node *prev = nullptr, *next = nullptr;
        Node(int k, int v) : key(k), val(v) {}
    };

    int capacity;
    std::unordered_map<int, Node*> cache;
    Node *head, *tail; // Dummy sentinel nodes

    void addNode(Node* node) {
        node->next = head->next;
        node->prev = head;
        head->next->prev = node;
        head->next = node;
    }

    void removeNode(Node* node) {
        Node* prevNode = node->prev;
        Node* nextNode = node->next;
        prevNode->next = nextNode;
        nextNode->prev = prevNode;
    }

    void moveToHead(Node* node) {
        removeNode(node);
        addNode(node);
    }

    Node* popTail() {
        Node* res = tail->prev;
        removeNode(res);
        return res;
    }

public:
    LRUCache(int cap) : capacity(cap) {
        head = new Node(-1, -1);
        tail = new Node(-1, -1);
        head->next = tail;
        tail->prev = head;
    }

    int get(int key) {
        if (cache.find(key) == cache.end()) return -1;
        Node* node = cache[key];
        moveToHead(node); // Mark as most recently used!
        return node->val;
    }

    void put(int key, int value) {
        if (cache.find(key) != cache.end()) {
            Node* node = cache[key];
            node->val = value;
            moveToHead(node);
        } else {
            Node* newNode = new Node(key, value);
            cache[key] = newNode;
            addNode(newNode);

            if (cache.size() > capacity) {
                Node* lru = popTail(); // Evict least recently used!
                cache.erase(lru->key);
                delete lru;
            }
        }
    }
};

2. Thread-Safe Singleton Pattern (Meyers' Singleton vs Double-Checked Locking)

In modern C++11, Meyers' Singleton is guaranteed thread-safe by the C++ standard (§6.7) with zero explicit mutexes: 

class DatabaseConnection {
private:
    DatabaseConnection() { /* Connect to DB */ }
    ~DatabaseConnection() = default;

public:
    DatabaseConnection(const DatabaseConnection&) = delete;
    DatabaseConnection& operator=(const DatabaseConnection&) = delete;

    // Guaranteed thread-safe initialization by C++11 runtime!
    static DatabaseConnection& getInstance() {
        static DatabaseConnection instance; // Initialized exactly once!
        return instance;
    }
};

⚠️ High-Frequency LLD & OOD Traps

Interview Traps
Trap #1: Liskov Substitution Principle (Square vs Rectangle)

The Question: "Should a Square class inherit from a Rectangle class in OOP?"

The Trap Answer: "Yes, because mathematically all squares are rectangles." (Fails interview!)

The Engineering Reality: No! In OOP, behavior matters, not mathematical taxonomies. If Square inherits from Rectangle:

void resize(Rectangle& r) {
    r.setWidth(5);
    r.setHeight(10);
    assert(r.getArea() == 50); // FAILS for Square! Setting height alters width to 10!
}

A client expecting a Rectangle will encounter broken invariants when passed a Square. This strictly violates the Liskov Substitution Principle (LSP).

Trap #2: Why Double-Checked Locking Failed in C++98 / Java 1.4

In naive double-checked locking without modern memory barriers:

if (instance == nullptr) {
    lock();
    if (instance == nullptr) {
        instance = new Singleton(); // HAZARD: Instruction reordering!
    }
}

The expression instance = new Singleton() involves 3 steps: (1) Allocate memory, (2) Construct object, (3) Assign pointer. Due to CPU out-of-order execution, the compiler may execute step 3 before step 2! Another thread checks instance == nullptr, sees a non-null pointer, and attempts to use the unconstructed object, causing crashes! In modern C++, solved via std::atomic with acquire-release memory order or Meyers' Singleton.

🎯 10 High-Frequency GFG Interview Q&As (Self-Assessment)

10 Questions
Q1: What is the difference between Factory Method and Abstract Factory?
• Factory Method: Uses inheritance to create a single product. Subclasses override the factory method to return a specific subclass (e.g. Dialog.createButton() returns WindowsButton or MacButton).
• Abstract Factory: Uses composition to create a family of related or dependent products without specifying their concrete classes (e.g. GUIFactory.createButton() AND GUIFactory.createCheckbox() for Windows vs Mac).
Q2: What is the difference between Strategy Pattern and State Pattern?
While both share nearly identical UML class structures, their intent differs completely:
  • Strategy Pattern: The client chooses a strategy algorithm upfront and passes it to the context. Strategies are independent and unaware of each other (e.g. Sorting via QuickSort vs MergeSort).
  • State Pattern: The context changes its behavior dynamically as its internal state changes. Concrete state classes hold references to the context and trigger state transitions (e.g. Vending Machine transitioning from NoCoinState → HasCoinState → DispenseState).
Q3: How do you design a Parking Lot system (Key Classes & Methods)?
Core class hierarchy for Parking Lot LLD:
  1. Vehicle (Abstract): licensePlate, VehicleType (Motorcycle, Car, Truck).
  2. ParkingSpot (Abstract): spotNumber, SpotType, isAvailable, park(Vehicle), vacate().
  3. ParkingLevel: levelNumber, List<ParkingSpot>, findAvailableSpot(VehicleType).
  4. ParkingLot (Singleton): List<ParkingLevel>, assignTicket(Vehicle), processPayment(Ticket).
  5. Ticket: ticketId, entryTime, spotNumber, feeCalculationStrategy.
Q4: What is the difference between Adapter, Facade, and Decorator patterns?
• Adapter Pattern: Converts an interface into an expected interface (translates between two incompatible interfaces without changing behavior).
• Facade Pattern: Simplifies a complex subsystem by providing a single higher-level unified interface (e.g. ComputerFacade.start() calls CPU, RAM, and HardDrive).
• Decorator Pattern: Dynamically enhances an object with new behaviors without modifying its interface (wraps an object while implementing the exact same interface).
Q5: Why is "Favor Composition Over Inheritance" a fundamental OOP guideline?
Inheritance creates tight compile-time coupling (White-box reuse); any change in the base class can break subclasses. It also leads to combinatorial class explosion (e.g. FastCar, SlowCar, ElectricFastCar, ElectricSlowCar).
Composition (HAS-A): Decouples behavior into pluggable components at runtime (Black-box reuse). A Car simply holds an Engine interface and a Transmission interface, allowing components to be swapped dynamically!
Q6: What is the Command Pattern and how does it support Undo/Redo?
The Command Pattern encapsulates a request as an object, complete with all information needed to execute the action.
• The command interface defines execute() and undo().
• An Invoker maintains an undo history stack: calling execute() pushes the command onto the history stack; clicking "Ctrl+Z" pops the command and calls its undo() method!
Q7: How do you design an Immutable Class in Java or C++?
An immutable class cannot be modified after construction:
  1. Declare the class as final (prevents subclasses from overriding methods).
  2. Make all fields private and final (or const in C++).
  3. Do not provide any setter / mutating methods.
  4. If fields contain mutable objects (e.g. Date, List), return deep defensive copies in getters and constructor!
Q8: What is the difference between Dependency Injection (DI) and Inversion of Control (IoC)?
• Inversion of Control (IoC): A general architectural design principle where the control of program flow is inverted from the application to a framework (e.g. Framework calls your code via lifecycle hooks).
• Dependency Injection (DI): A specific design pattern implementing IoC for object dependencies. Instead of a class creating its own dependencies (new Database()), dependencies are provided ("injected") from the outside via constructor, setter, or interface injection.
Q9: What is the Observer Pattern and how do you prevent Memory Leaks (The Lapsed Listener Problem)?
In the Observer Pattern, a Subject holds a list of Subscriber references.
The Lapsed Listener Problem: If an observer registers with a long-lived subject (e.g. global event bus), the subject retains a strong reference to the observer. Even if the observer is out of scope in the UI, the Garbage Collector cannot reclaim it, creating a severe memory leak!
Fix: Use Weak References (std::weak_ptr in C++ or WeakReference in Java) to hold observers in the subject's listener list.
Q10: What is the Template Method Pattern vs Strategy Pattern?
• Template Method: Uses inheritance. The base class defines the skeleton of an algorithm in a final method, deferring specific steps to abstract methods implemented by subclasses (Compile-time binding).
• Strategy: Uses composition. The context delegates the entire algorithm to a pluggable interface object (Runtime binding). Strategy is preferred when algorithms must be switched dynamically during program execution.
