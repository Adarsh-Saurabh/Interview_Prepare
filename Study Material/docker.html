# 📊 Container Architecture & OverlayFS Union Mounts

# OverlayFS Union Mount Architecture

OverlayFS Architecture: Merged, UpperDir, and LowerDir Layers
🔍
IMPORTANT Why Deleting a File Does NOT Shrink a Docker Image
Docker images are immutable stacks of read-only layers. • When a subsequent `RUN rm -rf /tmp/large_file.tar.gz` instruction executes, it cannot modify or delete the file from the preceding layer! • Instead, OverlayFS writes a **Whiteout character device** in the new layer that masks the file in the merged view. • Result: The file is hidden, but the image size STILL includes the full size of the file in the lower layer! Always download, extract, and clean up in a **SINGLE RUN instruction**.

TIP The Kubernetes Reconciliation Loop: Desired vs Current State
The core mental model of Kubernetes is an infinite control loop: $$\text{Reconciliation Loop}: \text{Observe Current State} \longrightarrow \text{Compare with Desired State in etcd} \longrightarrow \text{Take Action to Converge}$$ The Controller Manager continuously monitors etcd. If a node crashes, the Deployment controller detects `current replicas (2) < desired replicas (3)` and instructs the kube-scheduler to bind a new Pod to a healthy node.

# ⚡ Probes, Resource Limits & OOMKill vs CPU Throttling

# Container Health Probes & Resource Limits

Probe TypeFailure BehaviorProduction Role
Startup ProbeKubelet kills container and restarts it according to restartPolicyProtects slow-starting legacy apps from being killed by liveness probe
Liveness ProbeKubelet kills container and restarts itDetects deadlocks and unrecoverable app freezes
Readiness ProbeRemoves Pod IP from Service Endpoints (Zero traffic sent; does NOT kill pod!)Ensures traffic is only routed when warm and ready to serve
IMPORTANT Memory Limit vs CPU Limit: OOMKilled vs CPU Throttling
• **Memory Limit Exceeded**: Memory is a non-compressible resource. When a container exceeds its `limits.memory`, the Linux kernel OOM Killer immediately kills the process (`Exit Code 137: OOMKilled`)! • **CPU Limit Exceeded**: CPU is a compressible resource. When a container exceeds its `limits.cpu`, the kernel CFS scheduler throttles the process's CPU time slices. The process slows down, but is NEVER terminated!

# Production Kubernetes Deployment & Service Manifest

📄 production_k8s_deployment.yamlyaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  labels:
    app: order-service
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # Max pods created above desired count during update
      maxUnavailable: 0  # Zero downtime: never drop below 3 active pods!
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      containers:
      - name: api
        image: myregistry.io/order-service:v1.2.4@sha256:7b4f... # Pinned digest!
        ports:
        - containerPort: 8080
        resources:
          requests:
            cpu: "250m"      # 0.25 CPU cores guaranteed
            memory: "256Mi"
          limits:
            cpu: "500m"      # Throttled at 0.5 CPU cores
            memory: "512Mi"  # OOMKilled if exceeds 512Mi
        readinessProbe:
          httpGet:
            path: /health/ready
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
        livenessProbe:
          httpGet:
            path: /health/live
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 20
---

  name: order-service

  type: ClusterIP

    app: order-service

  - port: 80
    targetPort: 8080

# 🎯 High-Yield DevOps & Container Flashcards

Your Pod is stuck in 'CrashLoopBackOff'. Walk me through how you debug it.
P1 DevOps / SRE
1. Run `kubectl describe pod ` to check Events (inspect for image pull errors, failed readiness probes, or OOMKilled exit code 137). 2. Check application logs via `kubectl logs --previous` to see why the prior container crashed. 3. Check resource constraints: verify if the container breached memory limits. 4. If the container exits with Code 0 immediately, verify that its `CMD`/`ENTRYPOINT` runs a long-running foreground process rather than exiting immediately.
Rate Recall:
What is the difference between CMD and ENTRYPOINT in a Dockerfile?
P1 Docker Semantics
`ENTRYPOINT` defines the default executable binary that always runs when the container starts. `CMD` provides default arguments passed to the `ENTRYPOINT`. If both are provided, `CMD` arguments are appended to `ENTRYPOINT`. At runtime (`docker run my_image foo bar`), CLI arguments override `CMD` completely, but do NOT override `ENTRYPOINT` (unless `--entrypoint` is explicitly specified).
Rate Recall:
Why should you never pass production secrets via '--build-arg'?
P1 Security / DevSecOps
Any value passed via `--build-arg` is permanently recorded in the image's metadata and layer history (`docker history `), allowing anyone with read access to the image to extract the plaintext secret! Solution: Use Docker BuildKit Secret Mounts: `RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret`, which exposes the secret ephemerally in RAM during build without baking it into any image layer.
Rate Recall:
What is the difference between a Volume and a Bind Mount?
P1 Storage Architecture
A Volume is managed entirely by the Docker daemon in host storage (`/var/lib/docker/volumes/`). It is isolated from the host filesystem core, safe from non-Docker host processes, and portable across OS platforms. A Bind Mount directly maps an arbitrary directory on the host machine (`/home/user/app`) into the container, exposing the container to host filesystem permissions and dependencies.
